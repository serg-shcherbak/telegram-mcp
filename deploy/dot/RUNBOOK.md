# Dot + Telegram: наблюдения за выбранными чатами

Этот каталог содержит воспроизводимый слой развёртывания. Основной MCP, Telegram-клиент и обработчики событий работают в одном процессе. Отдельный асинхронный worker доставляет пакеты; вторая Telegram-сессия не создаётся.

Базовый `compose.yaml` оставляет Events выключенными. Существующие ручные read/send-инструменты сохраняются. Старые общие ring/debounce producers и фоновый прогрев всех диалогов отключены в этом deployment. Конкретные наблюдения, подписки и ключи при сборке не создаются.

## Сборка и предварительная проверка

Из корня проверенного checkout:

```sh
export TELEGRAM_DOT_IMAGE="local/telegram-dot:$(git rev-parse --short=12 HEAD)"
docker build -f deploy/dot/Dockerfile \
  --build-arg VCS_REF="$(git rev-parse HEAD)" \
  -t "$TELEGRAM_DOT_IMAGE" .
docker compose -f deploy/dot/compose.yaml config --no-env-resolution --quiet
```

Образ устанавливает зависимости из `uv.lock` с extra `events`. `.dockerignore` разрешает только исходники и необходимые сборочные файлы: session, `.env`, состояние, тестовые данные и локальная история в build context не входят. Контейнер работает как UID/GID 1000, слушает только опубликованный loopback-порт и сохраняет ограничения ресурсов текущего сервиса.

Перед заменой сервиса зафиксируйте его image ID и состояние, идентификаторы и время старта соседних контейнеров, а также статус существующих News/ScentAI. Проверьте владельца смонтированных session/app-каталогов. Снимите отдельную резервную копию собственного состояния сервиса; Telegram session и ключи требуют отдельного защищённого хранения.

Обновление выполняется только для `telegram-mcp` через адресный `compose up -d --no-deps telegram-mcp` с нужным compose-файлом и проверенным image tag. Не используйте общий `down`, перезапуск Docker или перезапуск соседних служб. После замены сравните статус и время старта соседей, проверьте основной MCP и частный tunnel.

## Подготовка локального режима Events

Потребуются существующая авторизованная Telegram file session, подтверждённый числовой ID аккаунта и приватное подключение MCP. В env сохраняются проверенные настройки ручного deployment: on-demand транскрипция, эксклюзивная блокировка session и явная область ручного чтения. Разрешение ручной отправки и `ask_before_writes` проверяются отдельно.

Пользователь создаёт новый ключ Fernet и отдельные случайные ключи профилей непосредственно на сервере защищённым способом. Ключи не вводятся в чат и не печатаются в диагностике. Существующий master key нельзя перезаписывать: он нужен для чтения сохранённых подписок.

Файл [profiles.example.json](profiles.example.json) намеренно содержит пустые ключи и непригодный ID. Заполните собственную копию вне checkout. Нужен один ручной профиль; каждый context-профиль содержит явные watch ID. Контекстный профиль можно добавить после создания и просмотра draft наблюдения.

Пример путей:

| Назначение | Путь контейнера |
|---|---|
| Events DB | `/app/state/events/events.sqlite` |
| Master key | `/run/events/master.key` |
| Профили доступа | `/run/events/profiles.json` |

Каталог DB должен принадлежать сервису и иметь режим `0700`, DB — `0600`. Ключ и профили хранятся вне каталога DB, в обычных файлах `0600`, доступных UID сервиса. Symlink для них запрещён. Для образа с UID 1000 файл root:root `0600` недоступен; владелец и режим проверяются до запуска. Ключ не включается в резервную копию DB.

Явно задайте `DOT_EVENTS_DB`, `DOT_EVENTS_KEY_FILE`, `DOT_EVENTS_PROFILES_FILE`. Локальные функции включаются через `DOT_EVENTS_ENABLED=1`. Доставка остаётся выключенной: `DOT_EVENTS_DELIVERY_ENABLED=0`, `DOT_EVENTS_CONTEXT_VERIFIED=0`. Включённый режим использует разные Bearer-ключи ручного и фонового профилей; подключение клиента должно передавать соответствующий ключ на обычные MCP-запросы и Events.

## Один выбранный чат

1. Через ручной профиль найдите нужного заказчика и точный marked chat ID. Для темы подтвердите её существование. Не используйте глобальное наблюдение.
2. Подготовьте draft через `watch_prepare`, выбрав поддержанные source capabilities. Посмотрите `watch_preview`: чаты, темы, хранение метаданных, учёт обращений, запуски и уведомления.
3. Подтвердите точную версию и активируйте её через `watch_activate`. Начальная граница — текущее время. История до неё автоматически не анализируется.
4. Добавьте этот watch ID в context-профиль и перезапустите только собственный сервис с обновлённой конфигурацией. Проверьте, что context-ключ видит только scoped-инструменты, а попытка вызвать широкое чтение или отправку завершается отказом.
5. Проверьте выбранный чат в локальном режиме: чужие чаты не дают строк, собственный ответ учитывается тихо, темы не смешиваются. Перезапуск должен сохранить состояние, бюджет и границы доступа. Покрытие восстановления остаётся ограниченным.

Сервер принимает create/edit и достоверно привязанные delete. Удаление без однозначного чата отбрасывается. Подтверждённая потеря доступа при выбранной сверке приостанавливает watch. Универсальный поток всех изменений доступа, реакции, read receipts, папки follow и прочие расширения не объявлены рабочими обработчиками.

## Приёмка Dot и включение доставки

На стороне ChatGPT предоставьте Dot только нужный context-профиль. Одновременно доступный широкий ручной connector позволяет читать шире watch. Проверьте реальный список инструментов и права фоновых внутренних записей анализа. После этого оператор может выставить `DOT_EVENTS_CONTEXT_VERIFIED=1` и отдельно разрешить доставку. Флаг фиксирует выполненную проверку, а не выполняет её сам.

Проведите приёмку на одном явно согласованном чате:

- Rescan показывает Events и scoped-инструменты на нужном подключении.
- `events/subscribe` приходит на тот же аутентифицированный endpoint с конкретным watch ID и scope revision; подписанный callback challenge подтверждён.
- Совпавшее событие получает webhook `2xx`, появляется в правильном Work/Dot и приводит к свежему анализу. Несовпавший чат не доставляется.
- Серия реплик даёт пакет, исходящий ответ не создаёт самостоятельного запуска, устаревший анализ не сохраняется.
- Отдельно проверены тихое выполнение и видимые ответы. До этого используются консервативные лимиты пакетов: каждый POST считается потенциально видимым запуском.
- Unsubscribe, пауза, сужение области, отзыв профиля и истечение срока останавливают ожидающую доставку. Приём запроса, уже начавшего передачу, фиксируется отдельно.

Совместимость Events с реальным Dot и частным tunnel должна быть проверена здесь. Успех локального ASGI-теста или fake callback не закрывает этот gate. Публичный endpoint без аутентификации не используется как обход.

## Поведение и восстановление

Три внешних события: `telegram.activity.batch_ready`, `telegram.attention.due`, `telegram.watch.health_changed`. Входящие, исходящие, reply и media — признаки исходных сообщений внутри пакета. Десять признаков не означают десять независимых событий.

Предложения по умолчанию: settling 45 секунд, max wait 180 секунд, минимум 300 секунд между запусками; 6 запусков/watch/час и 20/владелец/час, 3 потенциально видимых сигнала/watch/час и 10/владелец/час. Пока независимое тихое выполнение не доказано, действует меньший лимит. Повторы POST и replay тоже расходуют бюджет. Тихие часы изначально отсутствуют. Одноразовый recheck задаётся отдельной явной операцией; создание watch не запускает повторяющиеся напоминания.

SQLite хранит ограниченные метаданные, обращения, подписки, outbox, позиции и бюджеты. Пакеты имеют устойчивые ID; повтор после сбоя сохраняет тот же ID и тело. Подпись и её timestamp обновляются. `2xx` подтверждает приём платформой, а не завершённый анализ. `410` и `413` не повторяются. Остальные разрешённые повторы ограничены сроком подписки, возрастом события и числом попыток.

По умолчанию подписка получает конечный срок до 24 часов; refresh продлевает разрешённую жизнь. Cursor привязан к владельцу, подписке и epoch. Retention и ограниченное replay отражаются `truncated`, а потерянная или неоднозначная история — coverage gap. После паузы начинается новая граница; неделя старых оповещений не воспроизводится автоматически.

Переполнение и ошибки переводят функцию в ограниченное состояние. Не удаляйте журнал незаметно ради освобождения места: используйте предусмотренные retention и revoke/delete. Старые выводы, не имеющие доказательств в текущей области доступа, не выдаются фоновому профилю. Для восстановления смысла требуется новая ограниченная сверка.

## Откат и фактическая проверка

Чтобы отключить функцию, верните базовый compose с `DOT_EVENTS_ENABLED=0` и перезапустите только `telegram-mcp`. Укажите ранее проверенный image tag для отката образа. Сохраните DB и соответствующий master key раздельно. Старый несовместимый читатель не должен открывать новую схему DB. Отключение функции само по себе не является удалением пользовательских данных.

В этом изменении локально проверены реальные SQLite-транзакции и HTTP-путь закреплённого MCP SDK, fake Telegram-клиенты, подписи и защищённый сетевой backend. Wheel содержит пакет Events; Compose прошёл проверку конфигурации. Сборка Docker-образа требует доступного daemon. Реальные Dot/tunnel, аккаунт Telegram, сервер и соседние службы относятся к отдельной приёмке; сама подготовка PR их не меняет.
